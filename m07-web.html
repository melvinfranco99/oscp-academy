1. La idea clave

El formulario de la gestoríaUn empleado copia literalmente lo que escribes en la casilla “nombre” dentro de una orden que luego ejecuta su jefe. Si en la casilla escribes, además del nombre, “…y dale las llaves de la caja fuerte”, y el empleado lo copia sin mirar, el jefe obedecerá. Casi todas las vulnerabilidades web son esto: la aplicación confía en lo que escribe el usuario y lo mezcla con instrucciones.

Referencia del sector: OWASP Top 10, la lista de los riesgos web más importantes (control de acceso roto, fallos criptográficos, inyección, diseño inseguro, mala configuración…).

3. Inyección SQL (SQLi)

SQLLenguaje para hablar con bases de datos: SELECT * FROM usuarios WHERE nombre = 'ana'.

El fallo aparece cuando la aplicación construye la consulta pegando texto del usuario:

❌ Vulnerable 
$u = $_POST['user'];
$sql = "SELECT * FROM users
        WHERE name = '$u'";
✅ Corregido (consulta parametrizada) 
$st = $pdo->prepare(
  "SELECT * FROM users WHERE name = ?");
$st->execute([$_POST['user']]);

Si el usuario escribe una comilla ', en la versión vulnerable rompe la estructura de la consulta y la base de datos da un error de sintaxis. Esa es la primera señal que se busca: un carácter especial cambia el comportamiento de la página. A partir de ahí, un atacante puede alterar la lógica de la consulta para saltarse un login o leer otras tablas.

TipoCómo se nota
Basada en erroresLa página muestra el error SQL
Basada en UNIONLos resultados de otra consulta aparecen en la página
Ciega booleanaLa página cambia ligeramente entre una condición verdadera y una falsa
Ciega por tiempoLa respuesta tarda más cuando la condición es verdadera
Impacto en el OSCPUna SQLi puede dar credenciales (tabla de usuarios con hashes) o, en algunos motores (p. ej. MSSQL con xp_cmdshell habilitado), ejecución de comandos. Recuerda: sqlmap está prohibido en el examen, así que debes entender la técnica manual. Practícala en PortSwigger Academy (sección SQL injection).

4. Path traversal e inclusión de archivos (LFI/RFI)

El archivadorPides “el informe de marzo” y el empleado va a la carpeta informes/marzo. Si pides “sube dos carpetas y dame la agenda del director”, y el empleado no comprueba, te la dará.

En las rutas, ../ significa “sube una carpeta”. Si una web hace index.php?page=contacto y el código abre el archivo indicado sin validar, se podría salir de la carpeta prevista y leer archivos del sistema (como /etc/passwd, que todos pueden leer, de ahí que sea la prueba típica).

VarianteQué consigue
Path traversalLeer archivos fuera de la carpeta web
LFI (Local File Inclusion)El servidor además interpreta el archivo incluido (p. ej., como PHP). Si el atacante logra meter código en un archivo local (logs, sesiones, subidas), se convierte en ejecución de código
RFI (Remote File Inclusion)Se incluye un archivo de otro servidor. Requiere configuraciones inseguras (allow_url_include)

Qué leer si encuentras uno (en tu lab): archivos de configuración de la web (credenciales de base de datos), claves SSH de usuarios, y en Windows archivos como C:\Windows\win.ini como prueba.

Mitigación: lista blanca de valores permitidos, no pasar rutas desde el usuario, realpath() y comprobar que el resultado queda dentro de la carpeta permitida.

5. Inyección de comandos

Ocurre cuando la web ejecuta un comando del sistema con datos del usuario. Ejemplo típico: una herramienta “haz ping a esta IP” en un panel de administración.

❌ Vulnerable 
ip = request.args["ip"]
os.system("ping -c 1 " + ip)
✅ Corregido 
ip = ipaddress.ip_address(request.args["ip"])
subprocess.run(["ping", "-c", "1", str(ip)])

La shell interpreta caracteres especiales como ;, &&, | o $( ) como “y después ejecuta otra cosa”. Si la entrada no se valida, el usuario podría encadenar comandos propios. La corrección: validar el dato (que sea realmente una IP) y pasar los argumentos como lista, sin shell.

6. Subida de archivos

Si una web permite subir archivos y luego los guarda en una carpeta accesible y ejecutable por el servidor, subir un script del lenguaje del servidor (p. ej. .php, .aspx) equivale a ejecutar código.

Defensa débilPor qué falla
Comprobar solo la extensión con una lista negraExisten extensiones alternativas que el servidor también ejecuta (.phtml, .php5…)
Comprobar el Content-TypeLo envía el cliente: se cambia en Burp
Comprobar los “magic bytes”Se pueden anteponer al contenido

Defensa correcta: lista blanca de extensiones, renombrar el archivo, guardarlo fuera de la raíz web o en una carpeta sin permisos de ejecución, y comprobar el contenido.

7. Cross-Site Scripting (XSS)

La web muestra texto del usuario sin “escaparlo”, y el navegador de otra persona lo interpreta como código JavaScript. Permite robar sesiones o actuar en nombre de la víctima.

TipoDónde se guarda
ReflejadoEn la URL; la víctima tiene que abrir un enlace
AlmacenadoEn la base de datos (comentarios, perfiles): afecta a todos los que lo ven
DOMEn el JavaScript del propio navegador
RelevanciaEn el OSCP el XSS es poco frecuente como vía de entrada (no suele haber “víctimas” navegando). Las estrellas son SQLi, LFI, subida de archivos, inyección de comandos y software vulnerable o mal configurado.

8. Otras vías muy frecuentes

🔑 Credenciales por defecto

admin/admin, tomcat/tomcat, las del manual del fabricante. Pruébalas siempre en paneles (Tomcat, Jenkins, phpMyAdmin, routers).

🧩 CMS desactualizados

WordPress, Joomla, Drupal y sus plugins. wpscan enumera versión, plugins y usuarios de WordPress.

🔢 IDOR

Cambiar ?factura=1001 por 1002 y ver la de otro cliente. Falta de control de acceso.

📂 Archivos expuestos

Carpeta .git, copias .bak, phpinfo.php, backups de la base de datos.

Prácticas

Laboratorios recomendados (gratis y legales)PortSwigger Web Security Academy: rutas de SQL injection, Path traversal, OS command injection, File upload. DVWA (Damn Vulnerable Web App) en tu propia máquina virtual. TryHackMe: “OWASP Top 10”.
Fácil Identifica el tipo de fallo

(a) ?file=informe.pdf y la página muestra el contenido de otro archivo al cambiar el nombre. (b) Un campo “buscar” devuelve “You have an error in your SQL syntax” al escribir una comilla. (c) Un formulario de “ping” devuelve más líneas de las esperadas al añadir un punto y coma.

Solución: (a) path traversal/LFI, (b) inyección SQL basada en errores, (c) inyección de comandos.

Solución (ejemplo): “Sustituir la concatenación de cadenas por consultas parametrizadas (prepared statements) en todas las consultas a la base de datos. Aplicar validación de entrada por lista blanca y ejecutar la aplicación con un usuario de base de datos con los mínimos privilegios. Desactivar los mensajes de error detallados en producción.”

Reto Cadena de ataque

Explica cómo una LFI en una web podría acabar en acceso SSH, sin ejecutar ningún exploit.

Solución: con la LFI se leen archivos de configuración de la web (por ejemplo, el que conecta con la base de datos) que contienen una contraseña. Esa contraseña se reutiliza en la cuenta de un usuario del sistema (visto en /etc/passwd) y permite entrar por SSH. O bien se lee la clave privada SSH del usuario (/home/usuario/.ssh/id_rsa) si los permisos lo permiten. Lección: la reutilización de contraseñas convierte una lectura de archivos en acceso completo.
